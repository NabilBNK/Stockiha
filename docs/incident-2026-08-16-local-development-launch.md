# Incident Report: Local Development Launch and Migration Recovery

**Date:** 16 August 2026
**Scope:** Local Windows R8 acceptance environment
**Affected database:** `stockiha_r8e_verification_test` on PostgreSQL 18 / port 5433
**Status:** Resolved and verified

## Summary

Stockiha initially started its Tauri process but showed **Service unavailable**.
After the local launcher was used, startup advanced to SQLx migrations and
failed with `permission denied for table _sqlx_migrations`. Subsequent
recovery exposed migration metadata drift, role-state leaks in historical
migrations, a direct-purchase backfill blocked by the posted-receipt
immutability trigger, and a small frontend type error.

The local database, runner, migration, and frontend type contract were
repaired. The application now launches through `run.bat` and displays the
native **Sign in** page.

## Symptoms

1. Running `npm run tauri dev` showed:

   ```text
   [DB_POSTING_ERROR] pool timed out while waiting for an open connection
   ```

   The frontend rendered **Service unavailable**.

2. Running `run.bat` then stopped before Tauri launch:

   ```text
   error returned from database: permission denied for table _sqlx_migrations
   ```

3. Once that permission issue was repaired, SQLx identified an altered
   historical migration checksum and later a missing/out-of-order migration
   entry.

4. The final direct-purchase migration failed because its compatibility
   backfill attempted to update posted purchase receipts, which are correctly
   protected by an immutability trigger.

5. The frontend production build then failed because `ProcurementCopy` did
   not declare three fields already supplied by every locale.

## Verified Causes

| Layer | Cause | Evidence |
|---|---|---|
| Runtime launch | A stale development URL targeted port `55432`, while the isolated PostgreSQL cluster listened on `5433`. | Authenticated readiness against the stale target failed; PostgreSQL was listening on `127.0.0.1:5433`. |
| SQLx metadata | `public._sqlx_migrations` was owned by `stockiha_admin` rather than `stockiha_migrator`. | The migrator had no `SELECT`, `INSERT`, or `UPDATE` privilege. |
| Migration history | The local metadata included an earlier temporary checksum for `20260803125900` and an invalid placeholder checksum for `20260813000000`; `20260812120000` was missing despite a later migration being marked installed. | `sqlx migrate info` reported the differing checksum and pending migration. |
| Migration role state | Historical migrations changed to `stockiha_owner` but did not consistently restore the effective role before SQLx wrote its metadata row. | Transaction probes finished as `stockiha_owner`; that role intentionally has no metadata-table write privilege. |
| Direct-purchase backfill | `20260816150000` updated historical posted receipts without a migration-scoped exception to the update trigger. | PostgreSQL rejected the update with `procurement posted receipt records are immutable`. |
| Frontend contract | Locale objects used `previouslyReceived`, `confirming`, and `optionalNote`, but the shared TypeScript type omitted them. | `npm run build` type errors. |

## Resolution

### Local database repair

- Restored the SQLx metadata table owner to `stockiha_migrator`.
- Reconciled the one historical checksum only after verifying that the
  migration's canonical table/function ownership postconditions already held.
- Removed the guarded invalid placeholder metadata row for
  `20260813000000`, then let SQLx apply the actual migration in order.
- Reconciled the other role-reset-only checksum changes back to their
  canonical repository bytes.

No business rows, posted ledgers, or credentials were deleted. The invalid
SQLx metadata row was regenerated by the real migration.

### Source changes

1. `scripts/run-sqlx-migrations.ps1`

   - Clears inherited `PGOPTIONS` for deterministic migration sessions.
   - Verifies that SQLx metadata is owned by `stockiha_migrator`.
   - Uses a short-lived `SELECT`/`INSERT`/`UPDATE` bridge for
     `stockiha_owner` while SQLx runs historical migrations that intentionally
     change role.
   - Revokes the bridge in `finally` and fails if any privilege remains.

2. `20260816150000_direct_purchase_foundation.sql`

   - Disables only `purchase_receipts_forbid_update` while performing the
     deterministic `receipt_origin` compatibility backfill.
   - Re-enables the trigger immediately in the same transaction.
   - Resets the owner role before SQLx records migration completion.

3. Frontend

   - Completed the `ProcurementCopy` type contract.
   - Replaced one non-reassigned test variable with `const` to satisfy lint.

## Prevention and Operating Procedure

Use the launcher, not a bare Tauri command:

```powershell
Remove-Item Env:STOCKIHA_DEV_DATABASE_URL -ErrorAction SilentlyContinue
.\run.bat
```

The launcher starts/checks PostgreSQL, applies migrations, builds the frontend,
and starts Tauri. Do not place database credentials in tracked files or paste
runtime key contents into logs, screenshots, or reports.

When a migration fails:

1. Stop at the SQLx error; do not bypass it by launching Tauri directly.
2. Inspect metadata ownership, applied versions, checksums, and effective
   session roles.
3. Do not use SQLx force/ignore options to hide a checksum mismatch.
4. Reconcile metadata only after proving the database postcondition matches
   the canonical migration; otherwise reprovision the disposable acceptance
   database.
